## Что это такое

antimage — это две программы и CLI:

- **`antimage-panel`** — плоскость управления. Обслуживает операторский API и
  веб-интерфейс по HTTP, а также gRPC-плоскость управления, в которую агенты
  подключаются по mTLS.
- **`antimage-node`** — агент. Работает на каждом управляемом сервере,
  регистрируется, затем удерживает долгоживущий поток к панели и приводит хост
  к желаемому состоянию, которое публикует панель.
- **`antimage-ctl`** — локальное администрирование и восстановление; работает
  напрямую с базой данных панели. Это путь обратно внутрь, когда UI недоступен
  или заблокированы все администраторы.

Центральное проектное решение — **согласование желаемого состояния поверх
потока, инициируемого агентом**, а не императивный RPC. Панель публикует, как
узел *должен* выглядеть; агент сам решает, как этого достичь, и сообщает, что
он сделал. Благодаря этому узлам не нужен входящий порт, отключившийся узел
самовосстанавливается по возвращении, а расхождение конфигурации
обнаруживается, а не молча перезаписывается.

## Архитектура

```
                    ┌──────────────────────────────┐
   operator ──HTTP──►  antimage-panel              │
   (browser/CLI)     │  ├─ HTTP API + embedded SPA │  :8080
                     │  ├─ gRPC control plane      │  :8443  (mTLS)
                     │  ├─ SQLite (WAL)            │
                     │  └─ private CA              │
                     └───────────▲──────────────────┘
                                 │ agent dials out; no inbound port on the node
                     ┌───────────┴──────────────────┐
                     │  antimage-node (agent)       │
                     │  ├─ enrol (one-time token)   │
                     │  ├─ control stream (mTLS)    │
                     │  └─ adapter: observe → plan  │
                     │              → apply → verify│
                     └──────────────────────────────┘
```

**Ревизии.** Каждое изменение желаемого состояния узла проходит через
единственную узкую точку, которая канонизирует документ (RFC 8785 JCS),
хэширует его алгоритмом SHA-256 и увеличивает `desired_revision` ровно на
единицу. `applied_revision` продвигается только тогда, когда агент сообщает о
сходимости **и** применённый им хэш совпадает с хэшем, записанным панелью.
Совпадение ревизии при расхождении хэшей — это нарушение целостности, а никак
не сходимость.

**Двухуровневая авторизация.** Каждый запрос проходит явную проверку
разрешения `rbac.Check`, и каждый ограниченный по области запрос независимо
применяет SQL-предикат области видимости. Пропуск любой из двух проверок
заметен сам по себе, потому что каждая тестируется отдельно.

## Возможности

- Несколько администраторов с четырьмя встроенными ролями: `super_admin`, `admin`, `reseller`, `readonly`
- Ограничение доступа по узлам, реализованное в SQL, а не только в обработчиках
- Журнал аудита, работающий только на добавление, охватывающий привилегированные
  действия, отказы авторизации и отклонения при валидации
- Непрозрачные серверные сессии (не JWT), поэтому отзыв действует немедленно
- Двухфакторная аутентификация TOTP с одноразовыми кодами восстановления
- Ограничение частоты попыток входа и блокировка учётной записи
- Регистрация узла по одноразовому токену и через собственный частный УЦ
- Отзыв через список разрешённых: удаление узла немедленно закрывает доступ его сертификату
- Согласование желаемого состояния с обнаружением расхождений и пошаговыми отчётами о применении
- Актуальный статус узлов через Server-Sent Events
- Начальная установка по SSH с закреплением ключа хоста, учётные данные никогда не сохраняются
- Веб-интерфейс с принудительной поддержкой письма справа налево и интернационализацией

## Требования

**Хост панели**
- Linux x86-64 или ARM64
- ~200 МБ на диске для бинарного файла, базы данных и журнала аудита; растёт вместе с размером парка
- Никакой внешней базы данных, брокера сообщений или кэша — только SQLite

**Управляемый узел**
- Debian 11/12/13 или Ubuntu 20.04/22.04/24.04, x86-64 или ARM64
- `systemd`, `curl`
- Исходящий TCP до gRPC-порта панели. **Входящий порт не требуется.**

**Сборка из исходников**
- Go 1.26 или новее
- Node.js 20+ и npm (только для сборки веб-интерфейса)

| Компонент | Поддерживается | Проверено |

## Установка

### Клонирование и сборка

```bash
git clone https://github.com/devprogrmer/antimage.git
cd antimage
```

Сначала соберите веб-интерфейс — панель встраивает его в себя:

```bash
cd web && npm ci && npm run build && cd ..
```

Затем бинарные файлы:

```bash
make build
```

Или без `make`:

```bash
CGO_ENABLED=0 go build -trimpath -o bin/antimage-panel ./cmd/antimage-panel
CGO_ENABLED=0 go build -trimpath -o bin/antimage-node  ./cmd/antimage-node
CGO_ENABLED=0 go build -trimpath -o bin/antimage-ctl   ./cmd/antimage-ctl
```

`CGO_ENABLED=0` выбран намеренно: драйвер SQLite написан на чистом Go, поэтому
бинарные файлы статические и не требуют libc на целевой машине.

### Запуск панели

```bash
sudo mkdir -p /var/lib/antimage && sudo chmod 700 /var/lib/antimage
sudo ./bin/antimage-panel \
  --data-dir /var/lib/antimage \
  --http :8080 \
  --grpc :8443 \
  --grpc-hosts panel.example.com
```

При первом запуске панель генерирует свой мастер-ключ, свой частный УЦ и свою
базу данных. Она выводит отпечаток УЦ, который вы закрепите на узлах:

```
level=INFO msg="antimage-panel listening" http=:8080 grpc=:8443 ca_fingerprint=… grpc_cert_hosts=[panel.example.com]
```

> **`--grpc-hosts` должен перечислять имена, к которым агенты действительно
> обращаются.** Они становятся SAN-именами TLS-сертификата панели.
> Несовпадение разом ломает рукопожатие каждого узла и остаётся невидимым,
> пока агент не попробует подключиться.

### Создание первого администратора

```bash
sudo ./bin/antimage-ctl --data-dir /var/lib/antimage \
  create-admin admin 'a-long-passphrase' super_admin
```

Затем откройте `http://localhost:8080` и войдите.

### Установка панели как службы

```bash
sudo cp bin/antimage-panel /usr/local/bin/
sudo useradd --system --home /var/lib/antimage --shell /usr/sbin/nologin antimage
sudo chown -R antimage:antimage /var/lib/antimage
sudo cp packaging/antimage-panel.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now antimage-panel
```

Юнит выполняется как `User=antimage` с `NoNewPrivileges`, `ProtectSystem=strict`,
`ProtectHome` и `PrivateTmp`. **Вы обязаны создать этого пользователя** —
пакет этого за вас не делает.

## Добавление узла

### Однострочная начальная установка

Создайте узел в UI (или через `antimage-ctl`), возьмите токен регистрации и
выполните это **на узле**:

```bash
curl -fsSL https://panel.example.com/install.sh | sudo bash -s -- \
  --panel https://panel.example.com \
  --token YOUR_ENROLMENT_TOKEN \
  --ca-fingerprint THE_PANEL_CA_FINGERPRINT
```

`install.sh` проверяет ОС и архитектуру, скачивает агента и его SHA-256,
**проверяет контрольную сумму до установки**, записывает
`/etc/antimage/node.yaml` с правами 0600, устанавливает юнит systemd и
запускает его. Повторный запуск обновляет установку на месте, не расходуя
новый токен.

Передача `--ca-fingerprint` по внеполосному каналу — надёжный путь. Если вы его
опустите, скрипт получит отпечаток от панели по HTTPS — доверие при первом
использовании, которое можно обойти перехватом DNS-записи.

> **Чтобы однострочник заработал, вы должны опубликовать бинарные файлы
> агента.** См. [Загрузка бинарных файлов](#загрузка-бинарных-файлов).

### Установка вручную

```bash
sudo install -m 0755 antimage-node /usr/local/bin/antimage-node
sudo mkdir -p /etc/antimage /var/lib/antimage && sudo chmod 700 /var/lib/antimage
sudo tee /etc/antimage/node.yaml >/dev/null <<'YAML'
panel_url: https://panel.example.com:8443
token: YOUR_ENROLMENT_TOKEN
ca_fingerprint: THE_PANEL_CA_FINGERPRINT
state_dir: /var/lib/antimage
YAML
sudo chmod 600 /etc/antimage/node.yaml
sudo cp packaging/antimage-node.service /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now antimage-node
```

### Начальная установка по SSH из панели

`POST /api/v1/nodes/{nodeID}/bootstrap-ssh` запускает установщик по SSH в две
фазы: первый вызов возвращает отпечаток ключа хоста, чтобы человек его
подтвердил, а второй выполняется только против этого закреплённого ключа.
**Учётные данные SSH никогда не сохраняются** — ни таблицы, ни столбца, ни
сериализации — а ключевой материал стирается из памяти до того, как запрос
завершится.

## Конфигурация

### Флаги `antimage-panel`

| Флаг | Тип | По умолчанию | Обязателен | Назначение |
|---|---|---|---|---|
| `--data-dir` | путь | `/var/lib/antimage` | нет | База данных, мастер-ключ, загружаемые файлы. Права должны быть 0700. |
| `--http` | адрес прослушивания | `:8080` | нет | Операторский API и UI. Поставьте перед ним TLS-терминатор. |
| `--grpc` | адрес прослушивания | `:8443` | нет | Плоскость управления для агентов. Обслуживает mTLS напрямую. |
| `--grpc-hosts` | CSV | `localhost,127.0.0.1` | **фактически да** | DNS-имена и IP-адреса, к которым обращаются агенты; становятся SAN-именами сертификата. Значение по умолчанию годится только для локального тестирования. |
| `--version` | флаг | — | нет | Вывести версию и выйти. |

### Флаги `antimage-node`

| Флаг | Тип | По умолчанию | Назначение |
|---|---|---|---|
| `--config` | путь | `/etc/antimage/node.yaml` | Конфигурация агента. |
| `--version` | флаг | — | Вывести версию и выйти. |

### `/etc/antimage/node.yaml`

См. [`packaging/node.yaml.example`](packaging/node.yaml.example).

| Ключ | Тип | Обязателен | По умолчанию | Назначение | Замечание по безопасности |
|---|---|---|---|---|---|
| `panel_url` | строка | **да** | — | gRPC-эндпоинт панели, `https://host:port` или `host:port`. | Отклоняется при запуске, если содержит путь, строку запроса или схему, отличную от https. |
| `token` | строка | только при первом запуске | — | Одноразовый токен регистрации. | Стирается из файла, как только израсходован. Держите файл в режиме 0600. |
| `ca_fingerprint` | строка | **да** | — | SHA-256 сертификата УЦ панели, в шестнадцатеричном виде. | Запуск **отклоняет** конфигурацию без него, вместо того чтобы откатиться к системному хранилищу доверия. |
| `state_dir` | путь | нет | `/var/lib/antimage` | Ключ узла, сертификат, управляемое состояние. | Создаётся с правами 0700; ключ и сертификат — 0600. |
| `node_id` | int | нет | — | Записывается после регистрации. | Не задавайте вручную. |

| Переменная | Кем используется | Назначение | Замечание по безопасности |
|---|---|---|---|
| `ANTIMAGE_MASTER_KEY` | панель | 32-байтовый мастер-ключ в Base64 вместо файла ключа. | Шифрует секреты TOTP и закрытый ключ УЦ. Утёкшая база данных без этого ключа не даёт ни того, ни другого. ## TLS и mTLS

Плоскость управления взаимно аутентифицирована из конца в конец.

### Модель доверия

Панель держит **собственный частный УЦ**, создаваемый при первом запуске и
хранимый в зашифрованном виде под мастер-ключом. Это не публичный УЦ веб-PKI,
и он выпускает только:

- один **серверный сертификат** для gRPC-слушателя панели с SAN-именами из
  `--grpc-hosts`, действительный 90 дней и перевыпускаемый при каждом запуске
  панели;
- один **клиентский сертификат на узел**, `CN = <node id>`, действительный один год.

### Расположение сертификатов

| Что | Где | Права |
|---|---|---|
| Мастер-ключ | `<data-dir>/master.key` (или `ANTIMAGE_MASTER_KEY`) | 0600 |
| Сертификат УЦ + запечатанный ключ | таблица `panel_ca` в `<data-dir>/antimage.db` | — |
| Серверный сертификат панели | в памяти, перевыпускается при каждом запуске | — |
| Закрытый ключ узла | `<state-dir>/node.key` | 0600 |
| Сертификат узла | `<state-dir>/node.crt` | 0600 |
| Закреплённый УЦ панели | `<state-dir>/panel-ca.crt` | 0600 |

### Как работает регистрация

1. Агент генерирует свою пару ключей локально. **Закрытый ключ никогда не
   покидает узел, и панель его никогда не видит.**
2. Он подключается к панели и проверяет, что предъявленная цепочка содержит
   сертификат, чей SHA-256 совпадает с `ca_fingerprint`. Перехваченная
   DNS-запись ничего не даёт.
3. Он отправляет одноразовый токен и CSR.
4. Панель проверяет, что токен не использован, не истёк и привязан именно к
   этому узлу, подписывает клиентский сертификат, записывает его отпечаток и
   сжигает токен.
5. Всё дальнейшее идёт по mTLS.

Панель предъявляет `[leaf, CA]`, а не один лишь конечный сертификат, именно
затем, чтобы регистрирующийся агент — у которого ещё нет файла УЦ — смог найти
в цепочке свой закреплённый отпечаток.

### Проверка и отзыв

Слушатель использует `VerifyClientCertIfGiven`, а **не**
`RequireAndVerifyClientCert`: регистрация неизбежно происходит до того, как у
узла появится хоть какой-то сертификат. Управляющая служба навязывает это
требование на уровне каждого RPC и дополнительно сверяет предъявленный
отпечаток с `nodes.cert_fingerprint`.

**Отзыв — это список разрешённых, а не CRL.** Панель — единственный
проверяющий, поэтому удаление узла убирает его отпечаток и закрывает ему доступ
при следующем подключении. Нет ни CRL для распространения, ни OCSP-респондера,
который надо поддерживать.

### Срок действия и ротация

| Сертификат | Срок действия | Ротация |
|---|---|---|
| УЦ | 10 лет | Вручную. Его замена требует повторной регистрации всего парка. |
| Серверный панели | 90 дней | Автоматически — перевыпускается при каждом запуске панели. Перезапускайте панель не реже чем раз в 90 дней. |
| Клиентский узла | 1 год | **Пока не автоматическая — см. [Известные ограничения](#известные-ограничения).** |

### Команды проверки

Получить отпечаток, который операторам следует закрепить:

```bash
curl -fsS https://panel.example.com/api/v1/ca-fingerprint
```

Посмотреть, что предъявляет gRPC-слушатель:

```bash
openssl s_client -connect panel.example.com:8443 -showcerts </dev/null 2>/dev/null | openssl x509 -noout -text
```

Проверить собственный сертификат узла:

```bash
sudo openssl x509 -in /var/lib/antimage/node.crt -noout -subject -dates
```

## Аутентификация

- Пароли хэшируются алгоритмом **argon2id** (m=64 MB, t=3, p=4).
- Сессии — это **непрозрачные серверные токены**, а не JWT, поэтому отзыв
  вступает в силу немедленно. Хранится только SHA-256 токена.
- Куки помечены `HttpOnly`, `Secure`, `SameSite=Strict`.
- **Тайм-аут простоя 4 часа; абсолютный срок жизни 7 дней.** Активность
  продлевает окно простоя; абсолютный срок не продлевает ничто.
- Неудачные входы ограничиваются по частоте на учётную запись и на IP, а после
  5 неудач учётная запись блокируется. Неизвестное имя пользователя обходится в
  то же время, что и известное, поэтому по времени ответа нельзя понять,
  существует ли учётная запись.
- **TOTP** необязателен и включается для каждого администратора отдельно. После
  подключения требуется корректный код, и каждая ветвь, которую панель не может
  проверить, **отказывает**, а не пропускает по одному лишь паролю.
- Десять **одноразовых кодов восстановления** выдаются при подтверждении и
  показываются один раз.

Подключить второй фактор:

```bash
# returns {"secret":"…","provisioning_uri":"otpauth://…"}
curl -X POST https://panel.example.com/api/v1/auth/totp/enrol -b cookies.txt
# confirm with a code from your authenticator; returns the recovery codes once
curl -X POST https://panel.example.com/api/v1/auth/totp/confirm -b cookies.txt \
  -d '{"totp":"123456"}'
```

## Авторизация

Четыре встроенные роли:

| Роль | Чтение узлов | Запись узлов | Регистрация | Запись служб | Чтение аудита | Сессии |
|---|---|---|---|---|---|---|
| `super_admin` | ✅ все | ✅ | ✅ | ✅ | ✅ | ✅ |
| `admin` | ✅ в своей области | ✅ | ✅ | ✅ | ✅ | свои |
| `reseller` | ✅ в своей области | — | — | ✅ | — | свои |
| `readonly` | ✅ в своей области | — | — | — | — | свои |

Авторизация проверяется дважды, независимо:

1. **Проверка разрешения** — каждый обработчик вызывает `rbac.Check`, прежде
   чем что-либо делать.
2. **SQL-предикат области видимости** — каждый ограниченный по области запрос
   фильтрует по списку разрешённых для вызывающего, поэтому обработчик,
   забывший свою проверку, всё равно не сможет прочитать узлы другого
   администратора.

Отказы записываются в журнал аудита вместе с запрошенным разрешением, методом
и путём.

## Загрузка бинарных файлов

`install.sh` забирает агента с панели. Опубликуйте бинарные файлы, положив их
в `<data-dir>/downloads`:

```bash
sudo mkdir -p /var/lib/antimage/downloads
sudo cp antimage-node-linux-amd64 /var/lib/antimage/downloads/
sha256sum antimage-node-linux-amd64 | awk '{print $1}' \
  | sudo tee /var/lib/antimage/downloads/antimage-node-linux-amd64.sha256
sudo chown -R antimage:antimage /var/lib/antimage/downloads
```

Отдаются только эти четыре имени, и этот перечень — **список разрешённых, а не
санитайзер**:

- `antimage-node-linux-amd64` и `.sha256`
- `antimage-node-linux-arm64` и `.sha256`

Всё остальное возвращает 404, включая файлы, которые действительно лежат в
каталоге. Эндпоинт не требует аутентификации по замыслу — бинарный файл не
секрет, а право присоединиться даёт токен регистрации.

## Модель безопасности

| Свойство | Как обеспечено |
|---|---|
| Ключи узлов | Генерируются на узле; панель никогда не видит закрытый ключ. |
| Подмена панели | Агенты закрепляют отпечаток УЦ; перехваченная DNS-запись ничего не даёт. |
| Отзыв | Список разрешённых по `cert_fingerprint`; удаление узла немедленно закрывает ему доступ. |
| Секреты при хранении | Секреты TOTP и ключ УЦ запечатаны AES-256-GCM под мастер-ключом, который хранится **вне** базы данных. |
| Учётные данные SSH | Никогда не сохраняются. Ни таблицы, ни столбца, ни тега сериализации; стираются из памяти после использования. |
| Токены регистрации | Одноразовые, срок жизни 30 минут, хранятся в виде хэша, сгорают при использовании, вырезаются из записей аудита. |
| Обход каталогов | Загрузки используют список разрешённых **и** `os.OpenInRoot`, который отказывается выходить за пределы каталога даже через символические ссылки. |
| Целостность аудита | Только добавление; у `audit_log` нет внешнего ключа на `nodes`, поэтому удаление узла не может стереть его собственный след. |
| Расхождение | Управляемые файлы проверяются по контрольной сумме; правка вручную обнаруживается и исправляется, а не молча перезаписывается. |

Сообщайте об уязвимостях в соответствии с [SECURITY.md](SECURITY.md).

## Использование CLI

```
antimage-ctl [--data-dir DIR] <command> [arguments]

  create-admin   USERNAME PASSWORD ROLE   create an admin
  reset-password USERNAME PASSWORD        set a new password, revoke their sessions
  list-admins                             list admins with roles and status
  enroll-token   NODE_ID                  print a single-use enrolment token
  backup         DEST.db                  write a consistent database copy
  version                                 print the version
```

`reset-password` также очищает историю неудачных входов учётной записи, чтобы
попытки, заблокировавшие оператора, не держали его снаружи и дальше.

## Использование API

Все пути API находятся под `/api/v1`. Аутентификация — сессионная кука,
полученная из `POST /auth/login`.

```bash
# sign in
curl -c cookies.txt -X POST https://panel.example.com/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"…","totp":"123456"}'

# create a node, then mint a bootstrap command
curl -b cookies.txt -X POST https://panel.example.com/api/v1/nodes \
  -H 'Content-Type: application/json' \
  -d '{"name":"de-1","address":"203.0.113.10"}'

curl -b cookies.txt -X POST https://panel.example.com/api/v1/nodes/1/enroll-token
```

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/auth/login` `/auth/logout` | Жизненный цикл сессии |
| GET | `/auth/me` | Текущий субъект и его разрешения |
| POST | `/auth/totp/enrol` `/auth/totp/confirm` `/auth/totp/disable` | Второй фактор |
| GET/POST | `/nodes` | Список и создание узлов |
| GET/DELETE | `/nodes/{id}` | Детали узла; удаление закрывает узлу доступ |
| POST | `/nodes/{id}/enroll-token` | Выпустить одноразовый токен и команду начальной установки |
| POST | `/nodes/{id}/bootstrap-ssh` | Двухфазная начальная установка по SSH |
| GET | `/nodes/{id}/revisions` `/nodes/{id}/apply-runs` | История и пошаговые результаты применения |
| POST | `/nodes/{id}/services` | Создать службу (увеличивает ревизию) |
| PUT/DELETE | `/services/{id}` | Обновить или удалить службу |
| GET | `/audit` `/sessions` | Журнал аудита; собственные сессии |
| DELETE | `/sessions/{id}` | Отозвать одну из своих сессий |
| GET | `/events` | Актуальный статус узлов (SSE) |
| GET | `/ca-fingerprint` | Публичный якорь доверия (без аутентификации) |

Ошибки используют единую оболочку: `{"error":{"code":"…","message":"…"}}`.
Каждый ответ несёт `X-Request-ID`, который также появляется в журнале аудита.

## Логирование

Структурированные логи в stderr через `log/slog` из Go. Под systemd:

```bash
sudo journalctl -u antimage-panel -f
sudo journalctl -u antimage-node -f
```

Эксплуатационные события идут в **журнал аудита**, а не в stdout, и доступны
для запроса через `GET /api/v1/audit`. Секреты никогда не логируются: токены
регистрации вырезаются из вывода начальной установки, а секреты TOTP и коды
восстановления никогда не попадают в записи аудита.

## Проверка работоспособности

Живое представление — это `GET /api/v1/events` (SSE), который отправляет
снимок состояния каждые 3 секунды и **перепроверяет сессию на каждом такте**,
поэтому выход или отзыв быстро обрывает поток.

Значения статуса узла:

| Статус | Значение |
|---|---|
| `pending` | Создан, контакта ещё не было |
| `enrolling` | Токен выдан, регистрация ещё не завершена |
| `online` | Держит поток и шлёт heartbeat |
| `degraded` | Подключён, последнее применение не удалось или прошло частично |
| `integrity` | **Узел применил документ, хэш которого панель не выпускала.** Разберитесь. |
| `offline` | Нет heartbeat в течение трёх интервалов (90 с) |
| `disabled` | Отключён администратором |

## Устранение неполадок

**После переезда панели рукопожатие не проходит ни у одного узла.**
`--grpc-hosts` больше не совпадает с тем, к чему обращаются агенты. Проверьте
строку стартового лога (`grpc_cert_hosts=[…]`), исправьте флаг, перезапустите.
Панель перевыпускает свой сертификат при каждом запуске.

**`bad interpreter: /bin/bash^M` при запуске install.sh.**
Скрипт был выгружен с окончаниями строк CRLF. Репозиторий закрепляет `*.sh` за
LF через `.gitattributes`; клонируйте заново или выполните `dos2unix`.

**Администратор с подключённым TOTP не может войти, а в логе сказано, что
отсутствует box.**
Панель запустилась без своего мастер-ключа, тогда как зашифрованные секреты
существуют. Это намеренное поведение с отказом в закрытое состояние —
восстановите `master.key` или `ANTIMAGE_MASTER_KEY`. Не удаляйте ключ: без
него секреты TOTP и ключ УЦ невосстановимы.

**Узел завис в состоянии `integrity`.**
Применённый им документ хэшируется во что-то, чего панель никогда не выпускала.
Изучите `GET /api/v1/nodes/{id}/apply-runs`. Статус намеренно «залипает» —
heartbeat его не снимет.

**Начальная установка падает на шаге загрузки.**
Бинарные файлы не опубликованы. См. [Загрузка бинарных файлов](#загрузка-бинарных-файлов).

**`cannot VACUUM from within a transaction` при резервном копировании.**
Исправлено в этом выпуске. Обновите `antimage-ctl`.

## Процедура обновления

```bash
# 1. Back up first — this is consistent and safe while the panel runs.
sudo antimage-ctl --data-dir /var/lib/antimage backup /var/backups/antimage-$(date +%F).db

# 2. Replace the panel binary and restart. Migrations run automatically.
sudo systemctl stop antimage-panel
sudo cp antimage-panel /usr/local/bin/
sudo systemctl start antimage-panel

# 3. Publish the new agent binaries.
sudo cp antimage-node-linux-amd64 /var/lib/antimage/downloads/
sha256sum antimage-node-linux-amd64 | awk '{print $1}' \
  | sudo tee /var/lib/antimage/downloads/antimage-node-linux-amd64.sha256

# 4. Upgrade a node in place — re-running is idempotent and consumes no token.
curl -fsSL https://panel.example.com/install.sh | sudo bash -s -- \
  --panel https://panel.example.com --token '' \
  --ca-fingerprint THE_PANEL_CA_FINGERPRINT
```

Миграции базы данных выполняются только вперёд и запускаются при старте.
**Откатывайтесь восстановлением из резервной копии, а не понижением версии
бинарного файла.**

## Резервное копирование и восстановление

```bash
sudo antimage-ctl --data-dir /var/lib/antimage backup /var/backups/antimage.db
sudo cp /var/lib/antimage/master.key /var/backups/master.key   # 0600, store separately
```

`backup` использует `VACUUM INTO` из SQLite, создавая согласованную копию, пока
панель продолжает работать. Он отказывается перезаписывать существующий файл.

> **Одной базы данных недостаточно.** Без `master.key` закрытый ключ УЦ и все
> секреты TOTP невосстановимы. Делайте его резервную копию отдельно — хранение
> рядом с базой данных сводит на нет саму причину, по которой он живёт вне базы.

Восстановление:

```bash
sudo systemctl stop antimage-panel
sudo cp /var/backups/antimage.db /var/lib/antimage/antimage.db
sudo cp /var/backups/master.key  /var/lib/antimage/master.key
sudo chown antimage:antimage /var/lib/antimage/*
sudo systemctl start antimage-panel
```

## Удаление

На узле:

```bash
sudo systemctl disable --now antimage-node
sudo rm -f /etc/systemd/system/antimage-node.service /usr/local/bin/antimage-node
sudo rm -rf /etc/antimage /var/lib/antimage
sudo systemctl daemon-reload
```

Удалите узел и в панели — это уберёт его отпечаток из списка разрешённых.

На хосте панели:

```bash
sudo systemctl disable --now antimage-panel
sudo rm -f /etc/systemd/system/antimage-panel.service /usr/local/bin/antimage-panel
sudo rm -rf /var/lib/antimage      # destroys the database, CA, and master key
sudo userdel antimage
```

## Развёртывание

Поставьте TLS-терминатор перед `:8080`; `:8443` выставляйте напрямую, потому
что панель сама обслуживает там mTLS, а терминатор сломал бы проверку
клиентских сертификатов.

```
                 ┌── :443  → reverse proxy → :8080   (operators, HTTPS)
  panel host ────┤
                 └── :8443 → antimage-panel          (nodes, mTLS, direct)
```

Чек-лист: создайте пользователя `antimage`; `/var/lib/antimage` с правами 0700;
делайте отдельную резервную копию `master.key`; задайте `--grpc-hosts` равным
публичному имени; опубликуйте бинарные файлы агента; перезапускайте панель не
реже чем раз в 90 дней, чтобы серверный сертификат перевыпускался.

## Известные ограничения

Всё перечисленное реально и сделано осознанно для SP1:

- **Поставляется только адаптер-заглушка.** Он доказывает сходимость,
  обнаружение расхождений и отчётность из конца в конец, но не управляет ни
  одним реальным протоколом. Настоящие адаптеры — отдельный, более поздний
  подпроект.
- **Нет управления подписчиками, учёта трафика, квот и ссылок на подписку.**
  Вне рамок SP1.
- **Автоматическое обновление сертификата узла не реализовано.** Сертификаты
  действуют год; обновление на середине срока спроектировано, но не построено.
- **Нет UI для подключения TOTP.** Эндпоинты работают; в SPA для них пока нет
  экрана.
- **Нет глобальной настройки «требовать TOTP для super_admin».** Отложено
  намеренно: политика, запрещающая вход суперадминистраторам, которые не
  подключили TOTP, может полностью заблокировать оператора, и ей сначала нужен
  продуманный аварийный выход.
- **Значения перечислений, приходящие с сервера, отображаются без перевода**
  (`converged`, `ok`, `restart`). Это данные, а не строки интерфейса.
- **Коды TOTP не одноразовые.** Код остаётся действительным в пределах окна
  расхождения ±30 с.
- **Представление аудита не фильтруется по области.** Обладатель `audit:read`
  видит все строки, включая IP-адреса входов других администраторов. У
  `reseller` этого разрешения нет.
- **Нет эндпоинта метрик** (ни Prometheus, ни какого-либо другого).
- **Обратные миграции не протестированы.** Откатывайтесь восстановлением из
  резервной копии.
